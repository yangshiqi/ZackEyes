# ZackEyes MVP Design Spec

## Overview

ZackEyes is a macOS native app that turns the MacBook notch (Dynamic Island area) into a real-time control panel for AI coding agents. MVP focuses on a single-agent flow: Claude Code monitoring and permission approval via a notch overlay.

**Positioning:** Free alternative to Vibe Island ($19.99), with a free + premium model planned for later.

## Product Decisions

| Decision | Choice |
|----------|--------|
| Purpose | Competitive product targeting Vibe Island |
| Differentiation | Free core + premium upsell (usage analytics, team features) |
| Platform | macOS native (Swift/SwiftUI) |
| MVP scope | Single agent (Claude Code) + Notch panel + Permission approval |
| Brand | ZackEyes — independent brand, distinct from Vibe Island |
| UI form | Notch mode + menu bar fallback for notchless Macs |

## Architecture

Three components connected via Unix Domain Socket:

```
Claude Code                    Bridge CLI                     ZackEyes.app
(hooks in settings.json)  -->  (~/.zackeyes/bin/bridge)  <->  (SwiftUI + AppKit)
                               Swift binary ~200 LOC          /tmp/zackeyes.sock
```

### Component 1: Bridge CLI

- Lightweight Swift command-line tool, embedded at `ZackEyes.app/Contents/Helpers/bridge`
- Invoked by Claude Code hooks via a launcher script at `~/.zackeyes/bin/bridge`
- Receives hook event data via **stdin** (JSON from Claude Code)
- Connects to Unix Socket `/tmp/zackeyes.sock`
- For `PermissionRequest` / `AskUserQuestion`: synchronous — sends event, blocks waiting for response, outputs decision JSON to **stdout**
- For all other events: fire-and-forget — sends event, disconnects immediately
- If socket doesn't exist or connection fails: `exit 1` silently (non-blocking error — Claude Code logs it but proceeds normally)

**Exit code strategy:**
| Exit Code | Meaning | When to use |
|-----------|---------|-------------|
| `0` | Success, stdout JSON parsed | Normal response (permission decision, etc.) |
| `1` | Non-blocking error | Socket unreachable, timeout, crash — Claude Code proceeds normally |
| `2` | Blocking error | Never used by ZackEyes — we never block Claude Code |

**Timeout:** Bridge waits up to 15s for a PermissionRequest response. On timeout, `exit 1` — Claude Code falls back to its own terminal approval.

**Launcher script** (`~/.zackeyes/bin/bridge`):
```bash
#!/bin/zsh
# auto-generated by ZackEyes, do not edit
H=/Contents/Helpers/bridge
C="$HOME/.zackeyes/.app-path"
[ -f "$C" ] && read -r P < "$C" && B="${P}${H}" && [ -x "$B" ] && exec "$B" "$@"
for P in "/Applications/ZackEyes.app" "$HOME/Applications/ZackEyes.app"; do
  B="${P}${H}"; [ -x "$B" ] && exec "$B" "$@"
done
exit 1
```

### Component 2: Main App (ZackEyes.app)

SwiftUI application with these modules:

| Module | Responsibility |
|--------|---------------|
| `SocketServer` | Listens on `/tmp/zackeyes.sock`, accepts bridge connections, parses JSON events, sends responses |
| `SessionStore` | Maintains current Claude Code session state (idle/working/waiting/stopped) |
| `NotchPanel` | NSPanel overlay on the notch area, non-activating |
| `NotchViewModel` | ObservableObject driving the notch UI state |
| `MenuBarFallback` | NSStatusItem + NSPopover for notchless Macs |
| `HookInstaller` | Silent auto-injection of hooks into `~/.claude/settings.json` |

**App properties:**
- `LSUIElement = true` — no Dock icon
- Bundle ID: `app.zackeyes.macos`
- Minimum: macOS 14.0
- Zero third-party dependencies (no Sentry, no Sparkle in MVP)

### Component 3: Hook Auto-Installer

Silent, zero-interaction setup on app launch:

1. Check if `~/.claude/settings.json` exists
2. If exists: read, parse JSON, merge `hooks` key (append-only, never modify existing entries or other top-level keys like `permissions`, `enabledPlugins`, `defaultMode`, etc.)
3. If doesn't exist: check if `~/.claude/` directory exists; if so, create settings.json with hooks only
4. If `~/.claude/` doesn't exist: do nothing (Claude Code not installed)
5. Deploy launcher script to `~/.zackeyes/bin/bridge`
6. Write app path to `~/.zackeyes/.app-path` for launcher discovery

**Pre-write backup:** Always save `settings.json.backup.{timestamp}` before any modification.

**Hook configuration format** (must match Claude Code's nested schema — matcher omitted to match all):

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.zackeyes/bin/bridge --event PreToolUse"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.zackeyes/bin/bridge --event PostToolUse"
          }
        ]
      }
    ],
    "PermissionRequest": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.zackeyes/bin/bridge --event PermissionRequest"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.zackeyes/bin/bridge --event SessionStart"
          }
        ]
      }
    ],
    "SessionEnd": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.zackeyes/bin/bridge --event SessionEnd"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.zackeyes/bin/bridge --event Stop"
          }
        ]
      }
    ]
  }
}
```

**Merge strategy:** When `settings.json` already has a `hooks` key, iterate over each event name. For each event, append our hook group to the existing array — never replace or reorder existing entries. Identify our entries by the command path containing `zackeyes`.

## Hook Event Protocol

JSON messages exchanged over Unix Socket, newline-delimited.

### Bridge → App (Event)

The bridge forwards the full JSON received from Claude Code on stdin, plus adds a `_bridge_event` field:

```json
{
  "_bridge_event": "PermissionRequest",
  "session_id": "abc123",
  "hook_event_name": "PermissionRequest",
  "cwd": "/Users/ysq/Work/project",
  "tool_name": "Bash",
  "tool_input": { "command": "rm -rf /tmp/test" },
  "permission_mode": "default",
  "transcript_path": "/path/to/transcript.jsonl"
}
```

The bridge passes through all fields from Claude Code's stdin JSON unchanged, only adding `_bridge_event` for internal routing.

### App → Bridge (Response)

Only for `PermissionRequest` — bridge outputs this to stdout for Claude Code to parse:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PermissionRequest",
    "decision": {
      "behavior": "allow",
      "message": "User approved via ZackEyes"
    }
  }
}
```

**`behavior` values:**
- `"allow"` — approve the tool call
- `"deny"` — reject the tool call, `message` explains why

For `AskUserQuestion` (future), the response format uses `updatedInput` to pass answers back.

### Supported Hook Events (MVP)

| Event | Direction | Purpose |
|-------|-----------|---------|
| `SessionStart` | fire-and-forget | Session begins, show active indicator |
| `SessionEnd` | fire-and-forget | Session ends, clean up state |
| `PermissionRequest` | request→response | Show approval UI, return allow/deny |
| `PreToolUse` | fire-and-forget | Show current tool being executed |
| `PostToolUse` | fire-and-forget | Update tool execution result |
| `Stop` | fire-and-forget | Session stopped |

All hooks are synchronous (no `async` flag). Fire-and-forget events still run synchronously but the bridge exits immediately after sending to socket (< 10ms), so the blocking time is negligible.

### Protocol Rules

- One socket connection per hook invocation: connect → send → (wait response or disconnect) → close
- JSON delimited by `\n`
- If app not running (socket doesn't exist), bridge exits with code 1
- Bridge never uses exit code 2 — ZackEyes never blocks Claude Code

## Notch Panel UI

### Three States

**1. Collapsed (idle / no active session)**
- Notch area shows a small dim dot, visually blends with the native notch
- Nearly invisible when not in use
- `ignoresMouseEvents = true` — clicks pass through to menu bar

**2. Compact (session active)**
- Notch expands horizontally to ~320px pill shape
- Shows: status dot (color-coded) + "Claude Code" + status text + current tool badge
- Colors: green (#4ecdc4) = working, gray = idle, orange (#f5a623) = awaiting approval
- `ignoresMouseEvents = true` in non-interactive areas — only the pill itself is clickable
- Hover to expand to full panel

**3. Expanded (hover or permission request)**
- Full detail panel drops below notch area (~380px wide)
- Shows: session info, working directory, permission request details (tool name + command preview)
- Three action buttons: Deny (red) / Allow Once (teal) / Always (teal, stronger)
- Auto-expands when PermissionRequest arrives
- `ignoresMouseEvents = false` — full interaction enabled
- Non-activating — never steals focus from current app

### Interactions

- Hover over compact pill → expand with animation, toggle `ignoresMouseEvents` to `false`
- Mouse leaves expanded panel → 300ms delay → collapse to compact, toggle `ignoresMouseEvents` to `true`
- PermissionRequest arrives → force expand + optional sound alert
- Click outside → collapse

### NSPanel Implementation

```swift
class NotchPanel: NSPanel {
    init() {
        super.init(
            contentRect: .zero,
            styleMask: [.borderless, .nonactivatingPanel],
            backing: .buffered,
            defer: false
        )
        level = .screenSaver               // reliable z-order above menu bar
        isFloatingPanel = true
        becomesKeyOnlyIfNeeded = true
        isOpaque = false
        backgroundColor = .clear
        hasShadow = false
        isMovable = false                   // prevent space-switch drift
        ignoresMouseEvents = true           // pass clicks through in collapsed state
        collectionBehavior = [
            .canJoinAllSpaces,              // visible on all Spaces
            .stationary,                    // doesn't move with Space transitions
            .fullScreenAuxiliary,           // visible in full-screen apps
            .ignoresCycle                   // excluded from Cmd+Tab
        ]
    }
    override var canBecomeKey: Bool { true }
    override var canBecomeMain: Bool { false }
}
```

### Notch Detection and Geometry

```swift
extension NSScreen {
    var hasNotch: Bool {
        safeAreaInsets.top > 0
    }

    var notchSize: CGSize? {
        guard let leftWidth = auxiliaryTopLeftArea?.width,
              let rightWidth = auxiliaryTopRightArea?.width else { return nil }
        return CGSize(
            width: frame.width - leftWidth - rightWidth + 4,  // +4 visual alignment
            height: safeAreaInsets.top
        )
    }

    var notchFrame: CGRect? {
        guard let size = notchSize else { return nil }
        return CGRect(
            x: frame.midX - size.width / 2,
            y: frame.maxY - size.height,
            width: size.width,
            height: size.height
        )
    }
}
```

### Screen Configuration Changes

Observe `NSApplication.didChangeScreenParametersNotification` to handle:
- External display connect/disconnect
- Clamshell mode toggle
- Resolution changes

On notification: recalculate notch geometry, reposition panel, switch between notch mode and menu bar fallback if needed.

### Menu Bar Fallback

- Detect notch: `NSScreen.main?.hasNotch ?? false`
- No notch → `NSStatusItem` with `NSPopover` dropdown
- Identical content, different container

## Safety & Security

### Never Break User Configuration

1. **Hook injection protection**
   - Full backup before any write: `settings.json.backup.{timestamp}`
   - Append-only JSON merge — read → parse → merge `hooks` key only → write back
   - Never touch other top-level keys (`permissions`, `enabledPlugins`, `defaultMode`, `theme`, etc.)
   - Never modify or delete user's existing hook entries
   - If settings.json fails to parse: do not modify, show status warning in settings only
   - Identify our entries by command path containing `zackeyes` for safe removal

2. **Bridge defensive design**
   - Socket unreachable → `exit 1`, Claude Code proceeds normally
   - Socket response timeout (15s) → `exit 1`, Claude Code falls back to terminal approval
   - Bridge crash → `exit 1`, invisible to user
   - Never use `exit 2` — ZackEyes never blocks Claude Code
   - **Iron rule: ZackEyes failures must be invisible to the user's Claude Code experience**

3. **Clean uninstall**
   - "Remove Hooks" button in settings: finds entries with `zackeyes` in command path, removes only those
   - Cleans up `~/.zackeyes/`, `/tmp/zackeyes.sock`
   - Restores settings.json to pre-injection state (or removes hooks key if empty after cleanup)

### Performance Targets

| Metric | Target |
|--------|--------|
| Memory | < 30MB (pure native, no WebView) |
| CPU idle | ~0% (event-driven, socket accept blocks) |
| Bridge round-trip | < 10ms (connect, send JSON, disconnect) |
| UI updates | Only on state change, no continuous animation (except breathing dot via low-freq CADisplayLink) |
| Socket connections | Not reused — new connection per hook call, prevents leaks |

Launch ZackEyes → open terminal and run Claude Code → notch automatically shows session status → Claude Code requests permission → notch expands with approval panel → click Allow → Claude Code continues execution.

## Known Risks

### PermissionRequest Hook — Undocumented API

The `PermissionRequest` hook event is **not listed in Claude Code's official hook development documentation** (SKILL.md). It IS used by Vibe Island (a shipping product) and confirmed by multiple external sources, but carries inherent risk as an undocumented interface.

**Mitigation — dual-path strategy:**
- **Primary**: `PermissionRequest` hook → returns `hookSpecificOutput.decision.behavior`
- **Fallback**: If PermissionRequest doesn't work, switch to `PreToolUse` hook → returns `hookSpecificOutput.permissionDecision: "allow|deny|ask"` (this IS documented in SKILL.md)

The `PreToolUse` fallback fires earlier (before permission check) rather than at the permission dialog, so it's less precise but documented and reliable.

**Implementation plan:** Build a minimal verification test during Step 1 (Bridge CLI) to confirm PermissionRequest works before committing to the full UI.

### PermissionRequest Response Format — Inferred

The response format `hookSpecificOutput.decision.behavior` is inferred from Vibe Island reverse engineering and web research, not from official documentation. The `PreToolUse` response format `hookSpecificOutput.permissionDecision` IS documented and can serve as reference for the general pattern.
